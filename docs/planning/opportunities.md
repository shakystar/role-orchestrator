# 기회 검토: 관측과 자율적인 작업 운영

2026-11-19. 상태: **후보별 부분 구현·검증 진행 중**. 관측·전송 계약은 최소 구현했고, 내용 수준 작업 계약과 동적 작업 편성은 미완료다. 최신 구현 근거는 [계약·추적 검증](../contract-trace-validation.md), [SMS·지표 사전 검증](../workflow-feasibility.md)을 따른다. 아래는 최초 기획이며 완료 명세가 아니다. 사용자의 ‘기회단계’ 요청을 정식 편입 전의 기회·기획 검토 단계로 반영한다. 최소 연결 파일럿 통과와 정식 오케스트레이터 채택은 구별한다. 이번 변경은 문서만이며 설치·배포·새 모델 실행은 하지 않는다.

## 목표와 판단 기준

역할이 필요한 후속 검증을 제안하고, 오케스트레이터가 근거·작업 계약·예산에 따라 실행할 수 있게 한다. 실행 횟수나 반대 의견 수를 성과로 삼지 않는다. 같은 자료와 예산에서 근거 없는 결론, 불필요한 작업, 누락된 이견이 줄어드는지 확인한다.

현재는 역할 3개·4작업·수정 1회를 고정한 연결 실험이다. 동적 후속 조사, 관측 시스템, 기억 관리가 이미 구현된 것으로 해석하지 않는다. 도입 후보의 장점은 설계상 기대이며 성능 개선 측정 결과가 아니다.

## 작업 계약 초안 — O-02

작업에는 `task_id`, `role_ref/version`, `objective`, `hypothesis_refs`, `input_refs`, `expected_output_schema`, `acceptance_criteria`, `dependencies`, `allowed_capabilities`, `budget`, `scope_revision`을 명시한다. 모든 항목을 런타임 task에 복사하지 않고, 실행에 필요한 최소 정보만 어댑터로 전달한다.

구문·참조·정책 검사와 내용 판단을 분리한다. JSON 스키마 통과는 증거의 진실성을 보장하지 않는다. 구조 위반은 검증 실패, 자료 부족은 보류, 근거에 대한 이견은 재심 제안으로 구분한다. 형식 보정에도 한도를 두고, 실패했다고 원본 모델 작업을 자동 재실행하지 않는다.

## 후속 작업 제안 — O-03

에이전트는 `propose_task`, `request_evidence`, `challenge_assumption`의 구조화된 제안을 낸다. 각 제안은 어떤 불확실성을 해소하는지, 기존 근거와 무엇이 다른지, 필요한 역할·산출물·예산을 포함한다. 이러한 세 가지 동작은 우리 설계 제안이며 외부 프레임워크의 동일 명칭 API를 주장하는 것이 아니다.

오케스트레이터는 스키마·역할 목록·중복·순환·전체 작업 수·위임 깊이·예산을 검사한 후 기존 runtime에 작업을 제출한다. 정상 범위의 제안을 매번 사람에게 승인받는 구조로 만들지 않는다. 기존 권한 범위를 벗어나는 외부 행동은 별개다. 채택/거절/보류 이유와 근거를 기록한다.

초기 실험에서는 허용 역할 목록과 작은 작업 상한을 고정한다. 모델이 새 워커를 직접 만들지 않는다. SMS 도착만으로 작업 완료를 추정하지 않고 영속 완료 기록과 결과물 검증 뒤 graph 재개 이벤트를 생성한다. SMS 연동은 현재 파일럿에 없는 후속 구현이다.

## 컨텍스트와 결과물 — O-04/O-05

- 독립 검토: 목적·원자료·명시적 제약을 전달하고 다른 검토자의 결론은 최초 판단 이후 공유한다.
- 인수인계: 필요한 결정과 근거를 선택적으로 전달하며 전달 목록을 기록한다.
- 전체 대화 상속은 자동 기본값으로 삼지 않는다. 정보 부족과 공유 결론에 대한 동조를 모두 측정한다.
- 결과물은 짧은 요약과 불변 참조(버전/해시/출처/접근 수준)를 함께 반환한다. 구조화된 결과도 사실 검증을 대신하지 않는다.
- 자료를 찾지 못한 경우 ‘수요 없음’으로 변환하지 않는다. 요약·검색·기억 오류도 관측 대상으로 남긴다.

## 기억과 스킬 — O-07/O-08

역할 지침, 프로젝트 사실, 가설·판단, 작업 중간 상태를 구분한다. 기억 수정에는 근거·이유·이전 버전·유효 범위를 남긴다. 사용자 의견과 에이전트의 추측을 확정 사실로 저장하지 않는다. 정책·권한의 자기 수정은 기억 갱신과 별개로 다룬다.

이 단계는 DB 기반 16K/64K 페이지, LRU, 모델 컨텍스트의 2~10배 기억이라는 기존 아이디어를 대체하지 않는다. 페이지 크기와 교체 알고리즘은 토큰 예산·검색 정확도·요약 손실을 측정할 별도 후속 실험이다. Letta 사용만으로 OS와 같은 페이징이나 컨텍스트 확장이 달성된다고 주장하지 않는다.

## 검증 순서와 중단 조건

1. O-01/O-06: 기존 파일럿에 대한 관측 계약과 작은 고정 평가셋. 재개·캐시·오류를 연결하고 계측 비용을 기준 실행과 비교한다.
2. O-02: 작업 계약을 적용해 올바른 출력, 잘못된 참조, 자료 부족, 실제 반증의 처리 차이를 확인한다.
3. O-03/O-04/O-05: 같은 자료·모델·예산에서 고정 흐름과 제한된 후속 작업 제안 흐름을 비교한다. 독립 평가자는 조건을 가리고 결과를 검토한다.
4. 성과가 재현되면 정식 편입과 상세 기획을 결정한다. 기억·스킬은 그 뒤 별도 실험으로 진행한다.

제어 사례에는 잘못된 초기 전제뿐 아니라 올바른 전제, 기존 서비스로 해결된 사례, 판단 불가 사례, 중복 조사 제안도 포함한다. 개선을 위해 반드시 반대하거나 수정하게 만들지 않는다. 근거 없는 결론 감소, 불필요한 추가 호출, 입력 토큰, 비용 추정의 누락률, 실행 지연을 함께 보고한다. 측정하지 않은 품질 점수나 임의 종합 점수를 만들지 않는다.

관측 유실을 숨기거나, 재시도로 실제 작업이 중복되거나, 작업 상한을 우회하면 해당 실험은 실패다. 결과 품질 개선 없이 비용만 늘면 자율성 확장을 보류한다. 정량적인 합격 임계치는 기준 실행 분포와 표본 수를 확인한 뒤 비교 실험 전에 고정한다.

## 이번에 하지 않는 것

프레임워크 일괄 설치/포크, 신규 관측 저장소나 서버 생성, Langfuse Cloud 계정 등록·데이터 전송, 역할 수 확대, 사업 조사 재실행, 자동 자기 수정, 분산 운영. 현재 저장소 내 모듈 경계를 먼저 설계하고 독립 배포 수요가 생길 때 저장소 분리를 판단한다.

## 우선순위 조정 — 2026-11-19

사용자 결정: 내용 수준 작업 계약(O-02)보다 **SMS 기반 워크플로 연결 → 실행·사용량 지표 → 고정 평가셋**을 먼저 구현한다. 기존 bridge 전송 계약은 유지한다.

SMS/SQLite 연결의 5개 합성 검증은 통과했다. 이는 실제 동시 파이프라인이나 지표 집계기의 완성을 뜻하지 않는다. 실행 중 runtime 조회 API, 영속 이벤트·사용량 원장, 중복 제거 집계가 다음 구현 범위다. 자세한 검증 결과와 부족한 인터페이스는 [사전 검증](../workflow-feasibility.md)에 기록한다.

구현 준비 산출물: [SMS·집계 v1 경계와 수용 기준](workflow-metrics-v1.md). control API → inbox/graph 재개 → event 원장/집계 → 평가 runner 순서와 19개 수용 사례를 정의했다. API·원장 구현 완료를 뜻하지 않는다.
