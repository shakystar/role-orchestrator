# v0.2.0 · 개발 과제의 독립 리뷰팀 배정

**상태** 개발 준비. 계약 소유자는 role-orchestrator다. [통합 마일스톤과 검증 조합](https://github.com/shakystar/agent-eval/blob/32ba9808f68ed979ec1c9cdabd9b6a34620ce8f9/docs/milestones/v0.2.0/README.md). 기존 배정기의 호출법과 후보 검증 기록은 [독립 리뷰팀 배정](independent-review.md)에 있다.

## 사용자 동작과 범위

개발 책임자가 상위 오케스트레이터에 업무와 리뷰팀을 지정하면, 상위 실행은 검토할 산출물을 고정하고 팀에 업무 한 건을 위임한다. 호출자가 개별 구성원을 고르거나 두 번째 CLI를 수동으로 실행할 필요가 없어야 한다. 리뷰팀은 전문 판정과 최종 인수를 수행하며 결과를 원래 개발 과제에 돌려준다. 배포·병합 결정은 사람이 맡는다.

기존 후보에는 독립 리뷰팀 명부, 유형별 순차 배정기, 작성자와 검토자 중복 차단, 보완 요청, 영수증 재조회가 있다. v0.2.0의 새 개발 범위는 **상위 개발 과제와 이 배정기를 연결하는 접수·반환·재개 경로**다.

## 계약과 복구

상위 실행이 보관할 위임 예시는 다음과 같다. 예시의 식별값은 설명용이다.

```json
{
  "parent_task_id": "change-27",
  "revision": 1,
  "team": "independent-review",
  "task": "조회가 작업을 새로 제출하지 않는다는 인수 기준을 검토한다.",
  "kind": "criteria",
  "stateful": false,
  "authors": ["acl-001"],
  "evidence": {"criterion": "각 조회 요청의 submit 진입 횟수는 0이다."}
}
```

- 상위 오케스트레이터는 기존 과제에서 작성자 ID, 산출물 참조·해시, 기준 및 후보 커밋, 명부 SHA를 얻는다. 사용자가 보낸 작성자 목록과 영수증이 충돌하면 배정 전에 멈춘다. 리뷰 위임이 없는 기존 호출과 저장된 과제는 종전 방식으로 조회한다.
- 팀 브로커는 근거가 명확한 경우에만 검토 유형을 결정한다. 개발 단계에 인수 기준·반례·제품 패치·재현 결과·출처 대조 중 하나가 명시돼 있으면 기존 유형으로 매핑한다. 유형이나 패치의 상태 변경 여부를 확정할 근거가 없으면 필요한 정보와 입력 소유자를 반환한다. 이때 모델 호출은 0회다. 매 요청을 해석하는 별도 팀장 모델은 이번 필수 경로에 넣지 않는다.
- 배정 전에 상위 과제 ID·개정, 검토 유형, 상태 변경 여부, 입력 해시, 명부 SHA, 작성자와 예정 담당자를 저장한다. 같은 키의 동시 호출은 하나의 팀 상태를 공유한다. 같은 키로 증거를 바꾸면 거절하고, 보완본은 이전 개정과 연결한 새 개정으로 접수한다.
- 전문가는 `accept / revise / blocked`와 이유·책임자를 반환한다. 최초 `revise / blocked`에서 후속 역할 호출을 중단한다. 상위 실행은 보완할 근거·책임자와 기존 증거 참조를 보존한다. 전체 전문 판정이 수락되면 강이현의 최종 판정을 요청한다. `hold`는 실행 결과 불확실로 보존한다.
- 반환 레코드는 부모 과제·개정, 팀 상태·판정, 담당자, 근거, 산출물 해시, 역할별 시도 ID와 영수증 참조를 포함한다. 상위 기록 저장 전에 중단되면 같은 팀 상태에서 재조회한다. 이미 실행한 역할의 추가 제출은 0회여야 한다. 영수증을 확인할 수 없는 시도는 자동 재배정하지 않는다.

| 팀 입력 | 전문 역할 순서 | 최종 인수 |
|---|---|---|
| criteria / counterexample | 이서진(010) / 조하린(011) 중 해당자 한 명 | 강이현(005) |
| patch | 신도윤(012) → 상태 처리 변경 시 서민재(013) → 김가온(014) → 장유나(015) | 강이현(005) |
| reproduction / provenance | 김가온(014) / 장유나(015) 중 해당자 한 명 | 강이현(005) |

번호의 접두사는 `acl-`이다. 개발과 리뷰를 겸하는 구성원도 같은 고유 ID로 이해충돌을 검사한다. 모델과 추론 강도는 고정한 명부의 배정 계약에서 읽는다.

## 작업 분배

| 담당 | 산출물 | 착수 조건 |
|---|---|---|
| 요구사항·계약 담당 | 위임 및 반환 사례, 보완·불확실 상태 전이 | 위 표와 부모 과제 식별 방식 |
| Python 개발 담당 | 상위 개발 진입점의 위임·재개, 기존 배정기 호출, 부모 판정 저장 | 입력·반환 사례 확정 |
| 명부 담당 | 7인 고유 ID·보직과 모델 설정 대조 | 리뷰 명부 SHA |
| 회귀·증거 담당 | 기준 실패, 후보 통과, 추가 제출 횟수와 영수증 대조 결과 | 개발과 독립적으로 반례를 먼저 고정 |
| 런타임·어댑터 담당 | 기존 실행자·모델 경로 호환 검증 | 현재 공개 계약을 사용해 테스트 |

## 인수 기준과 검증

| ID | 상위 진입점에 가할 입력 또는 장애 | 통과 조건 |
|---|---|---|
| R1 | 기준 검토 한 건 | 010→005. 같은 부모 과제와 개정에 두 영수증이 연결되고 다른 구성원 호출은 0회 |
| R2 | 상태 변경 없는 패치와 상태 변경 패치 | 전자는 012→014→015→005, 후자는 012→013→014→015→005. 동일 패치 해시를 대조 |
| R3 | 유형 불명, 패치 상태 정보 누락, 작성자와 예정 검토자 중복 | 필요한 입력 또는 충돌 ID를 보고하고 전문가 제출 0회 |
| R4 | 전문가가 계측 근거를 반려한 후 수정본 제출 | 원 개정은 사유와 소유자를 반환하고 005 호출 0회. 새 개정의 판정·영수증은 원본과 구별 |
| R5 | 동일 요청의 동시 호출, 팀 판정 후 부모 기록 전 중단, 읽기 전용 재조회 | 역할별 실행 1회 이하. 재조회 추가 제출 0회. 입력 교체 거절. 영수증 누락 시 hold |
| R6 | 리뷰를 지정하지 않은 v0.1.x 과제와 과거 상태 | 기존 진입점·판정 조회 유지, 리뷰팀 추가 호출 0회 |

R1~R6은 실제 Go 브리지와 합성 응답으로 검증한다. 이어 고정한 상위 컨트롤러에서 실모델 과제 한 건을 빈 상태로 접수하고 팀 위임부터 부모 판정까지 연결한다. 검증 담당자는 모델을 다시 호출하지 않고 동일한 결과와 영수증을 대조한다.

## 준비 판단

기존 명부·배정기 회귀와 기술 통합 인수는 구별해 기록한다. 구현팀은 접수·반환 계약을 기준으로 작업하고, 검증팀은 동일 사례로 독립 반례를 먼저 작성할 수 있다. v0.2.0 상위 위임 경로의 인수는 미실행이다.

## 견본 모듈과 독립 코드 리뷰

견본은 Python의 `role_orchestrator/review_team.py`로 정한다. 작성자는 상위 진입점에서 팀 배정, 영수증 확인, 부모 판정 반환까지 추적할 수 있는 후보와 회귀 증거를 제출한다. 리뷰팀은 상태를 쓰는 주체, 저장·해시 바이트의 소비자, 재시작 후 재제출 결정을 각각 파일·심볼과 테스트로 연결한다. 이미 기준을 만족하는 경로는 기존 코드와 증거를 인용해 수락할 수 있다. 모듈 길이나 변경 줄 수를 목표로 삼지 않는다.

부모는 접수 시 정책 SHA와 명부 SHA를 따로 고정한다. 코드 리뷰 담당자는 기존 review-v1 응답을 유지하고 별도 증거 파일 `evidence/policy-review.json`을 작성한다. 파일에는 정책 SHA, 대상 저장소와 후보 SHA, 작성자·검토자 ID, 조항별 판정 목록을 둔다. 각 판정은 조항 ID, 경로·심볼, 관측값과 기대값, 영향, 증거 위치, 보완 조건과 책임자를 담는다. 부모 과제·개정 기록에는 이 파일의 경로와 SHA-256을 연결한다. 증거 누락이나 해시 불일치는 보류하고, 필수 수정은 기존 R4 경로로 작성자에게 반환한다. 코드 작성자와 독립 판정자가 같으면 R3를 적용한다.

| 기준 | 인수 방법 |
|---|---|
| Q1 정책 고정 | 부모 기록에서 접수 당시 정책, 후보, 검토자, 증거 파일을 찾아 오프라인에서 해시를 대조한다. |
| Q2 견본 판정 | Python 후보의 정상·실패·복구 경로와 관련 회귀 테스트를 독립 검토한다. 필수 수정과 증거 보류가 모두 해소되어야 수락한다. |
| Q3 리뷰 정확도 | 평가팀이 OWN-01, SER-01, REC-01에 대해 위반·허용 쌍을 각각 제출한다. 세 위반 모두 해당 조항으로 반려하고 세 허용 사례 모두 해당 사유로 반려하지 않아야 한다. |
| Q4 다른 언어에 적용 | Go의 `role-runtime/internal/control/approved_revision.go`를 읽기 전용으로 검토한다. 각 조항의 적용 여부와 이유를 심볼·호출자·검사에 연결한다. 수정이 필요하면 소유 팀에 후속 과제로 반환한다. |

정책 원본과 예외 승인 절차는 [프로젝트 개발 정책](https://github.com/shakystar/agent-collaboration-lab/blob/9bda89879d1587a74d91aff5d8f9d28c103542f6/docs/development-policy.md)을 따른다.
