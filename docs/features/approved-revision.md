# 승인된 수정 제안 한 건 실행

**상태** 개발 준비 · role-orchestrator 계약 소유 · 통합 목표 v0.1.0

## 사용자 동작과 범위

사용자가 저장된 검토 제안 중 revise 한 건을 승인하면 원래 작성자에게 같은 계약·산출물·검토 사유로 수정 한 번을 요청하고 나중에 결과를 조회한다. 기존 워크플로와 제안 기록은 그대로 읽는다. 조사·재검토 반복·자동 승인은 후속 범위다.

## 계약과 복구

공용 [계약 사례](../../contracts/approved-revision-v1.json)는 제품 구현 전 작성한 합성 입력이다. approve와 status의 논리 키는 (run_id, review_task_id)다. orchestrator가 저장된 검토 영수증에 연결된 산출물 해시와 조치를 확인한다. 해시가 다르면 conflict, revise 이외에는 unsupported다. 검증 후 키에 유일성 제약을 둔 승인 의도를 영속화한다. 최초 승인을 획득한 호출만 제출한다. runtime에 전달할 작업 ID는 이 키의 고정 JSON 배열을 UTF-8 공백 없이 직렬화한 SHA-256 소문자 hex로 정한다.

동시 승인과 재승인은 같은 작업을 조회한다. 진행 중에는 pending, 성공 영수증이 있으면 completed와 산출물 참조, 실패 영수증은 failed와 오류 코드를 반환한다. 영속 의도만 남고 제출 여부를 판정할 수 없으면 uncertain으로 보존한다. status는 제출하지 않는다. 기존 저장소에 승인 기록이 없는 경우 미승인 상태로 읽는다.

## 작업 분배

| 구성요소 | 담당 결과 | 착수 기준 |
|---|---|---|
| role-orchestrator | 명시적 승인·조회 진입점, 해시 검증, 의도 저장·복구 | 공용 사례의 가짜 runtime으로 시작 |
| role-runtime | 동일 작업 ID로 수정 실행 및 영수증 조회, 기존 인터페이스 재사용 여부 확인 | 동일 ID 동시 요청과 재시작 테스트부터 시작 |
| agent-eval | 요청·영수증·결과 참조 대조, 최초 실행과 재조회 간 추가 제출 수 확인 | 공용 사례를 읽어 독립 기대값으로 사용 |
| codex-adapter | 기준 버전의 실행 상태 계약 재사용 | 통합 회귀에서 확인 |

## 인수 기준과 검증

공용 사례의 new_dispatches는 해당 조작들로 새로 제출한 총횟수다. concurrent는 같은 입력을 동시에 두 번 승인한 뒤 완료까지 조회한다. receipt_only는 실행 성공 직후 Python 기록 전에 중단한 상태다. completed 사례는 같은 작업 ID와 영수증에 연결된 산출물을 반환해야 한다. 실패 영수증은 재승인해도 재제출되지 않아야 한다. 실모델 품질은 이번 인수 범위 밖이다.

준비 검사는 루트에서 `python3 -m json.tool contracts/approved-revision-v1.json`으로 사례를 읽는다. 구현 후에는 각 AGENTS.md의 검사와 실제 Go 프로세스 재시작을 포함한 fixture 통합을 실행해 시도 수와 영수증을 대조한다. 기능 인수 검사는 미실행이다.

## 준비 판단

세 레포는 같은 사례로 독립 테스트를 시작할 수 있다. 실제 연결 전 runtime의 수정 작업 제출 및 조회 진입점을 대조해 기존 계약으로 부족한 부분만 확장한다.
