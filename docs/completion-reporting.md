# 사용자 완료 보고 규격 v1

사용자 합의: 구현 목록도 유지하되, 먼저 **이전에는 어떻게 동작했고 지금은 무엇을 할 수 있는지**를 구체적으로 보여준다. 개발자의 변경 이력과 사용자가 이해하는 동작 변화를 함께 보고한다.

## 적용 범위

오케스트레이터가 사용자에게 개발·수정·검증 완료를 보고할 때 적용한다. 짧은 진행 상황 보고나 단순 질의 응답에 매번 전체 양식을 강제하지 않는다. 이 규격은 보고 지침이며 자동 보고 생성기 구현을 뜻하지 않는다.

## 기본 순서

1. **핵심 변화:** 이번 작업으로 가능해진 동작을 첫 문장에 쓴다.
2. **이전 → 현재:** 중요한 변화 2~5개를 구체적인 상황으로 비교한다. 변화가 하나면 표 대신 한 문장으로 충분하다.
3. **완료한 구현:** 각 동작을 가능하게 한 모듈·API·저장 방식 등을 짧게 연결한다. 구현 목록을 생략하거나 동작 설명으로 대체하지 않는다.
4. **검증과 적용 범위:** 무엇을 실제로 실행해 확인했는지, 합성/실제 모델 여부, 아직 적용하지 않은 경로를 구분한다.
5. **다음 경계:** 남은 작업과 필요한 다음 단계만 간단히 쓴다. 사용자가 결정할 일이 실제로 있을 때만 결정 사항을 제시한다.

커밋·문서 링크는 보조 근거로 마지막에 둔다. 파일 목록·테스트 개수·커밋 해시만으로 완료 보고를 끝내지 않는다. 작은 작업은 위 내용을 짧은 문단으로 합친다.

## 표현과 근거 규칙

- 이전 상태는 실제 직전 구현·검증 기록을 기준으로 한다. 개선을 강조하려고 기존 기능을 없었던 것처럼 설명하지 않는다.
- 내부 구현 완료, 실제 연결 완료, 합성 검증 통과, 실제 운영 검증을 서로 구분한다.
- 실행하지 않은 사례는 ‘가능할 것으로 예상’ 또는 ‘다음 검증 대상’으로 표시한다. 예시 시나리오를 성공 실적으로 표현하지 않는다.
- ‘안정성이 좋아졌다’보다 ‘완료 영수증 저장 후 종료돼도 재실행 없이 재개했다’처럼 조건과 결과를 쓴다.
- 속도·비용·자원 절감은 비교 측정이 있을 때만 주장한다. 내부 정리나 문서 변경은 사용자 동작이 바뀌지 않았다고 명시한다.
- 테스트 수는 보조 정보다. 무엇을 보장하는 검사인지와 미검증 범위를 함께 설명한다.
- 완료하지 못한 부분은 성공한 부분과 분리한다. 부분 구현을 전체 기능 완료로 확장하지 않는다.

## 이번 워크플로 개발에 적용한 예

| 상황 | 이전 | 현재 |
| --- | --- | --- |
| runtime이 작업 중일 때 상태 확인 | 순차 JSONL 파일럿과 프로세스별 검증 프로그램 사용 | 같은 소유 프로세스의 Unix 소켓 제어 API로 조회 가능 |
| SMS로 다음 역할 인계 | Go SMS와 LangGraph 재개를 별도 구성요소로 검증 | 영속 수신함·완료 영수증·산출물 확인을 거쳐 그래프 재개와 ack 연결 |
| 실행 지표 복원 | 상태 스냅샷과 관측 기록이 중심 | 영속 이벤트에서 중복 제거 집계를 만들고 새 DB로 재구축 가능 |

완료 구현: runtime 제어 API·이벤트 기록, Python workflow/inbox·metrics·평가 runner.
검증 범위: 합성 호스트의 19개 수용 사례. 모든 실제 모델 진입점 적용과 토큰·비용 집계는 후속 작업이다.
